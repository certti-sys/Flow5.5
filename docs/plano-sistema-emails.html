03Templates transacionais

O conteúdo do admin entra em template_colors.email_templates como { subject, greeting, message }. No envio, renderEmail (email.ts:173-236) faz:

  • welcome_template preenchido → HTML cru, ignora tudo que o admin editou na tela
  • Senão, templates[type] → subject/greeting/message interpolados e embrulhados no getBrandedWrapper
  • Sem template → input.html cru, sem wrapper e sem substituir variáveis

O wrapper tem CSS literal: fundo #f4f4f5, card #ffffff, cabeçalho #18181b, corpo #52525b, rodapé #fafafa, raio 16px. A única cor dinâmica é o botão, e vem de platform_settings.gradient_end_color — não de template_colors.primary. Ou seja: não existe caminho para trocar cor, logo, CTA ou estrutura.

Preview falso

O preview em EmailSettings.tsx:478-481 é um <div> React com bg-zinc-900 no botão — cores diferentes do envio real. Não usa getBrandedWrapper, não usa logo, não mostra o link real. É uma maquete, não uma prévia.

Vocabulário divergente: os defaults do painel usam {{nome}}, {{total}}, {{curso}}, {{aula}}, {{pagamento}}, mas os chamadores enviam user_name, product_name, cursos, itens, renewal_date… replaceVariables substitui chave exata; o que não casa fica literal no e-mail.

04Recuperação de carrinho

A coluna cart_recovery_settings.templates já é JSONB (20261123120000_cart_recovery_templates.sql:17-22) com estrutura { email: [{subject, body}], whatsapp: [{body}], sms: [{body}] } — não precisa de migration para virar HTML.

Hoje o admin edita assunto + corpo por estágio em AbandonedCarts.tsx:664-677, mas como texto. A edge transforma o corpo em <p>…<br>…</p> (cart-recovery/index.ts:209-224), então qualquer tag digitada aparece como texto. Não há preview no diálogo de edição, e o tipo enviado é sempre custom — que não está na lista do painel de E-mails.

Fixo no código: número máximo de 6 estágios, o link {link} (sempre SITE_URL/c/<slug>), o limite de 160 caracteres do SMS e o texto de fallback após o 3º contato.

05Campanhas

O editor é inline em EmailCampaigns.tsx:438-561: Nome, Assunto, Textarea de HTML e segmento. Não há preview dentro do editor. O preview existe só depois de salvar, no ícone de olho da tabela, com <iframe srcDoc> — e ele mostra o HTML cru, sem o rodapé de descadastro, sem o pixel e sem a reescrita de links que withTracking aplica no envio.

Sobre "não salva": o código de save ( :160-192 ) usa body_html de forma consistente em todo o caminho — banco, tipo gerado e edge. Não há bug de escrita. As causas prováveis são:

  • A campanha da sua conta está sent, e o botão Editar só aparece em draft|paused ( :392-409 ) — por isso só olho e lixeira
  • A validação de segmento aborta com "Escolha o segmento" se o filter_config herdado vier sem all_customers ( :166-169 )
  • O toast de sucesso é otimista: .update() não usa .select(), então não confirma se a linha persistiu
  • O efeito de contagem depende do objeto editor inteiro ( :117-124 ), dispara RPC a cada tecla e dá instabilidade

07Plano em 4 fases

F1
Campanhas: editar, salvar e previewar de verdade Editar em qualquer status (oferecer "Duplicar como rascunho" para sent), .update().select().single(), normalizar filter_config, preview dentro do editor usando a mesma função withTracking do envio (extrair para _shared). Dependência de contagem passa a ser os campos do segmento.
F2
Templates com HTML e preview real Campo html por tipo em email_templates + modo texto/HTML; renderEmail usa HTML com replaceVariables; alinhar os 7 tipos reais do back (remover 4 fantasmas, adicionar notification/custom); corrigir variáveis; expor ou eliminar welcome_template; edge preview-email admin-only gerando o HTML exacto com dados de exemplo.
F3
Carrinho com HTML e preview Aceitar is_html por estágio (sem migration, JSONB já existe); edge usa o HTML com variáveis quando marcado; preview no diálogo com as variáveis já listadas. Manter tipo custom, opt-out e teto de 6 estágios.
F4
Padronização do envio e das cores Fazer getBrandedWrapper ler template_colors (ou remover as cores para acabar com a ilusão); renderEmail sempre aplicar replaceVariables, inclusive em input.html; centralizar opt-out/tracking entre fila/carrinho/campanha sem perder o token por destinatário das campanhas.
Ordem recomendada

F1 → F2 → F3. F1 resolve a dor imediata (campanha) com risco baixo. F2 resolve a reclamação principal (editar HTML/cores com preview fiel). F3 cobre o carrinho. F4 é estrutural e pode vir depois — mexe no caminho de envio de todos os e-mails.

08Riscos e decisões

  • XSS: HTML do admin é conteúdo de confiança, mas variáveis como nome do aluno entram cruas (replaceVariables em email.ts:109-115). Escape obrigatório para valores de perfil
  • Senha temporária e login_url: viajam no corpo — nunca logar; já é o comportamento atual
  • Opt-out: custom, notification e streak_at_risk respeitam descadastro; alterar isso pode transformar aviso transacional em spam
  • Campanha enviada: editar o HTML depois do envio mudaria o que o destinatário vê no link de abertura — "duplicar como rascunho" é mais seguro que editar sent
  • Blindar preview: manter sandbox="" no iframe srcDoc
  • Decisão sua: quer que as 6 cores de template_colors passem a valer no wrapper, ou prefere remover o campo para não dar ilusão de edição?
