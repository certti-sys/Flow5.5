01O que você decidiu

Regras fechadas e registradas em AGENTS.md §4.30.

  • Periodicidade configurável no produto: mensal, trimestral, semestral ou anual
  • Nem todo gateway faz recorrência. O produto só pode marcar assinatura quando o gateway escolhido suportar
  • Híbrido: acesso já concedido continua legível; o bloqueio é de novidades, não de histórico
  • Bloquear, nunca apagar: não remover conta, não remover user_course_access
  • Drip travado enquanto não renovar / não pagar
  • Três notificações: lembrete de vencimento, lembrete de renovação e confirmação da renovação
Como isso difere do Getfy

O Getfy remove o acesso na expiração (SubscriptionAccessService::revokeAccessForSubscription faz detach). Você escolheu o contrário: manter a linha e bloquear. É uma decisão do Flow, não paridade — e é a correta para não apagar histórico nem âncora do drip.

03O limite dos gateways

Cada gateway tem uma API de assinatura diferente. Nenhuma está implementada no Flow hoje. O quadro abaixo é o que o código do Getfy e dos providers do Flow permite afirmar.

Consequência prática

O seletor de periodicidade no produto deve aparecer só quando o gateway suportar — exatamente como você pediu. O primeiro piloto é CajuPay, por ser o único com contrato validado na referência. Os demais entram como "em breve" até implementação específica. Mesmo no CajuPay, PIX automático exige adesão do lojista e mandato do pagador — é dependência externa, não só código.

05Regras de acesso e drip

Hoje a RLS de user_course_access e o helper auth_has_course_access só verificam existência da linha. Para bloquear sem remover, todos os pontos precisam passar a exigir status = 'active' e expires_at > now() quando a linha vier de assinatura:

  • Policy Users read own access
  • auth_has_course_access(uuid) (RLS de lesson_materials)
  • Edge lesson-file-url (PDF) e lesson-progress
  • get_course_release_map e _for
Ponto crítico: não reancorar

A renovação atualiza só expires_at. Se atualizar granted_at, o drip reposiciona a âncora e aulas já liberadas voltam a travar por release_after_days. É por isso que expires_at precisa ser coluna separada.

Com assinatura vencida, o aluno continua lendo o que já viu (material, PDF, progresso, comentários). O que trava é conteúdo novo: as RPCs de release devem devolver módulos e aulas futuros como bloqueados, inclusive os que não têm release_after_days.

07Riscos e decisões que ficam com você

  • Adesão do gateway: PIX automático (CajuPay, Efí, PushinPay) exige convenio e mandato do pagador. Sem isso, a recorrência não funciona — não é problema de código
  • Cartão recorrente: exige tokenização no gateway. O Flow hoje evita tocar dados de cartão (token é criado no SDK do Mercado Pago) — para CajuPay seria preciso aceitar o SDK dele
  • Estorno de parcela: cancela só o período ou a assinatura inteira? Hoje revoke_access_on_refund apaga acesso; no modelo híbrido deve virar bloqueio
  • Carência: quantos dias após o vencimento o conteúdo novo bloqueia? O Getfy usa grace_period_days = 0 por padrão
  • Outros gateways: Stripe/Asaas/MP/Pagar.me/PayPal ficam marcados como "sem recorrência" até implementação — você decide a ordem
Minha recomendação

Começar pela F1 (schema), que é reversível e não mexe em cobrança, depois homologar a F3 (acesso/drip) com assinaturas simuladas em banco — antes de depender de qualquer gateway real. A F2 fica para depois da adesão do CajuPay. Assim você valida o modelo híbrido sem risco financeiro.
